# 连接方式（出口）设计

Anyu 的浏览器流量永远只连内置内核的本机端口，闸门逻辑只有一份。三种连接方式的区别只在
内置内核的出站怎么拨：

| 方式 | 内核出站 | 选节点在哪 | 保证形态 |
| --- | --- | --- | --- |
| `system`（默认） | 直接拨所选节点，跟随系统路由 | Anyu | 结构型：关闸时内核规则全部拒绝 |
| `independent` | 拨所选节点，但出站套接字绑到系统选出的物理网卡，绕过宿主机 TUN | Anyu | 结构型，同上 |
| `external` | 不拨节点；唯一出站是一个指向本机 http/socks 端口的合成节点 | 宿主代理软件 | 监控型（见下） |

## 为什么有 independent

宿主机上的 mihomo 类 TUN（如 FlClash）若同时开了 `parse-pure-ip`、嗅探端口包含节点端口、
`override-destination`，会把内核发往节点 IP 的 Reality 握手按伪装 SNI 改写目标，导致连接
失败。让内核的出站套接字绑定物理网卡后，这条连接不进入宿主 TUN，嗅探无从改写。
实现：Windows 上用只读的路由/网卡查询选出上行网卡（`src/main/windows-egress.ts`），生成配置
时写入全局 `interface-name`。每次内核启动重新解析；解析不到可用网卡就保持关闭，不回退到
系统路由。目前只有 Windows 有解析器，其他平台选此方式时设置界面不提供、内核保持关闭。
Loon 的 SNI 嗅探只用于规则匹配、不改写目标，所以 `system` 方式经过 Loon 的 TUN 没有此问题。

旧版本（PR #1）的 `bypassHostTun` 布尔值在读入时迁移为 `connectionMode: 'independent'`。

## external 的监控与截断

`external` 不是浏览器直连外部端口：浏览器仍只连内置内核，内核把那个端口当作唯一节点。
因此暂停、关闸拒绝、断开现有连接、出口核对都照常工作。外部端口只接受本机地址
（127.0.0.1 / localhost / ::1）；局域网地址会让流量明文经过局域网，不支持。

最后一跳在宿主软件内部怎么选路，内核看不进去，所以这一方式靠监控补：

- 出口核对（启动、切换、每 5 分钟复测）经一个监控网址进行，默认是 Cloudflare 的
  `/cdn-cgi/trace`，用户可在设置里换成其他返回 `ip=` 与 `loc=` 两行的 trace 端点
  （`monitorUrl`）。只接受 https：这个端点的回答决定闸门开不开，明文回答可被路上任何
  一方伪造。
- 经监控网址测到的出口国家与配置不符、或请求失败（例如对方把这条路直连到了错误出口），
  核对不过，闸门关闭并断开全部连接。
- 局限如实标注在设置界面里：监控只抽查这一个网址。宿主软件若按域名分流，把监控网址走
  代理、把其他域名直连，本方式看不见。需要更强保证时，应在宿主软件里把这一路入站强制
  锁到代理组，或改用前两种方式。

## 不变的前提

- 任何方式下都没有直连出口：内核配置里不出现 DIRECT，关闸时只有探测一条路能出去。
- 方式或外部端口配置的变更先停旧路线再保存、再按新路线重启内核；只改监控网址时作废
  上一次核对结果并重新测量。
- 出口国家在三种方式下都必须核对一致才放行。
